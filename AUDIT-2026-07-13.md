# Alfred v2 — Structural Audit: Prioritized Roadmap

## Executive Summary

Alfred is a live, actively-operated system (6 systemd services, daily commits, real incident history) whose reliability engineering is genuinely good — the three major incidents (stale-PID crash-loop, LanceDB corruption, structlog crash) were each root-caused and fixed at the mechanism level, not patched over. The debt is concentrated in three places: **zero automated verification** on a fleet that performs destructive vault mutations, **copy-paste propagation** (6 near-identical config files, 6 systemd units, 4 independent reimplementations of the "don't re-ingest daemon output" invariant, 2 parallel budget-guard mechanisms) that has already produced silent drift (dead config keys, missing monitoring coverage for the 2 newest vaults, an undocumented live vault, a documented-but-dormant one), and **a quietly-regressed retrieval feature** (hybrid search silently became dense-only during the Milvus→LanceDB migration, with docstrings still claiming otherwise). None of this is on fire — the watchdog log shows ~6,200 quiet 5-minute cycles since June 5 — but the drift pattern is structural and will keep recurring with every new vault unless the copy-paste surface is templated. The single highest-leverage architectural question is whether the 6-processes-per-vault design is even necessary, since it's config-parameterized already and was the direct cause of the worst incident to date (PID-recycling collisions across instances).

## Structural Improvements

**1. Add locking to GraphStore and vault_ops.py** (~0.5 day, treat as a hard prerequisite)
`src/alfred/store/graph.py` and `core/vault_ops.py`'s `vault_create`/`vault_edit`/`vault_move` have zero lock usage, unlike `StateStore`'s `asyncio.Lock` pattern. Currently masked only by everything running on one event loop with synchronous writes — becomes a real corruption race the moment any daemon's file I/O moves to a thread pool (surveyor's embedding/HDBSCAN work already does). Mirror `StateStore`'s lock pattern now.

**2. Config templating — base config + systemd template unit** (1-2 days)
`AlfredConfig.load()` does a flat `yaml.safe_load` per file with no include/merge mechanism, so 70-85% of every `config-*.yaml` is byte-identical copy-paste — the direct mechanical cause of the dead-key drift, the untuned-vaults drift, and the systemd-unit duplication. Fix: a `config-base.yaml` merged under each override (or move identical blocks into dataclass defaults), one `alfred@.service` template using `%i`, and a config-loader startup check that warns on any YAML key present but not consumed. Resolves config-drift, budget-tuning-drift, and systemd-duplication simultaneously — they share one root cause.

**3. Single source of truth for the vault/service roster** (1 day, depends on #2)
The vault list is independently declared in 5 places (`config-meta.yaml`, `RUNBOOK.md`, live systemctl units, watchdog's array, game-guard's array) with confirmed disagreement across all three most load-bearing lists. Generate watchdog/game-guard arrays from `config-meta.yaml` at deploy/start time; add an `alfred create-vault <name>` scaffolding script. Two of the last two vault additions (employment, content) each independently dropped a different step — an observed 2-for-2 failure rate on the manual process.

**4. Split JanitorDaemon and ConsolidatorDaemon along responsibility lines** (2-3 days)
JanitorDaemon (607 lines) bundles structural lint/autofix, LLM stub-backfill, O(n²) weekly dedup, and 90-day session archival behind one scheduling failure boundary. ConsolidatorDaemon does the same with cluster labeling, synthesis, and stub-page generation. A slow path in either's least-tested responsibility has blast radius against unrelated daemons. Split into separate daemon classes or separate APScheduler job registrations.

**5. Shared MCP tool-registration module** (1 day)
`server.py`, `server_http.py`, and `meta_server.py` duplicate tool bodies byte-for-byte and have already drifted (quick win #9). Extract shared tool bodies into `mcp/tools.py`, centralize `QueryOptions` defaults in one constants module.

**6. Stand up a minimal test tier** (2-3 days for the first slice, ongoing)
Zero test files exist; `pytest`/`pytest-anyio` are declared but never installed. Target the system's actual failure history rather than broad coverage: (a) a concurrency test for the new GraphStore lock, (b) golden-path tests for the unified `is_daemon_generated` predicate, (c) a config-loader test asserting every set YAML key is actually consumed (would have caught both dead keys immediately), (d) a retrieval-mode assertion that BM25/sparse actually contributes to ranked output once quick win #5 is resolved.

**7. Investigate the OOM/SIGKILL source behind LanceDB corruption** (1-2 days of instrumentation)
The self-heal (batch-per-file commits + quarantine + circuit breaker) is well-designed defense-in-depth but doesn't identify what's killing the process mid-commit. Correlate `journalctl` OOM-killer/SIGKILL events with quarantine trips so each future quarantine is diagnosed, not just recovered from — each one currently forces a full-vault re-embed (real bursty compute cost).

**8. Evaluate consolidating the per-vault process model** (exploratory spike, 2-3 days to prototype)
Six OS processes each run a full independent APScheduler + StateStore + LanceDB connection + all 5 daemons, differing only by config. Nothing in the daemon logic requires process-level isolation. A single multi-tenant process keyed by `vault_id` would cut per-process overhead ~6x, coalesce curator's 6 independent 10s polls — and notably, this exact multi-process design was the root cause of the worst incident to date (PID-recycling collisions, 492 restarts in one day). Flagged as a deliberate go/no-go decision point, not a default — no documented failure mode currently requires per-vault fault isolation, and consolidating would also collapse structural improvement #3's coverage-drift problem.

**9. Resolve DISTILL-REDESIGN.md's status** (<1 day to decide)
Dated 2026-06-20, "PROPOSED — for review," 100% unimplemented, and its own diagnosed problem (unbounded log/data growth) has recurred unfixed. Predates the employment vault. Decide explicitly: resume it, or archive/delete it so it stops representing phantom planned-but-abandoned work.

## Things That Are Fine — don't rewrite these

- **The three major incident fixes are genuinely root-caused, not patched.** PID-recycling (starttime-based PID files), LanceDB corruption (batched commits + quarantine + circuit breaker + inbox alert), and the structlog crash (one-line fix converging onto the existing logging pattern) all show real diagnosis and verification. This team root-causes rather than firefights — worth preserving that discipline as the codebase grows.
- **`StateStore`'s locking pattern itself** is well-designed — the gap is inconsistent use and not extending it to GraphStore/vault_ops, not that the pattern is wrong. Extend it, don't replace it.
- **The distiller's `cron('hour=2')` + one-shot catch-up job design** — a genuinely subtle, correct fix for the restart-resets-interval flaw. Leave as-is.
- **Curator's cost optimization** (skip classification when frontmatter already declares type) and **surveyor's fail-open retry behavior** (leave a file untouched on upsert failure so it retries) are deliberate, correct design choices — not bugs.
- **`meta_server.py`'s data-driven `_build_engines`** loops `config-meta.yaml`'s vault list with no hardcoded names — exactly the right pattern. It's the surrounding operational lists (watchdog, game-guard) that need to catch up to it, not the meta server that needs changing.
- **`GraphStore`/`StateStore` themselves** show no duplication or backend-ambiguity issues.
- **`BM25Store`'s offline/`bm25_only` path** is a distinct, intentionally-designed fallback for lightweight second-machine deployment — don't lump it in with the milvus.py dead-code cleanup.
- **The watchdog's game-guard-awareness fix (23d4bfc)** is a good example of the system catching its own bug via its own escalation path — the self-correction loop works; only the coverage lists feeding it need consolidating.
- **The stdio/HTTP/meta MCP server split** is architecturally sound — maps to three genuinely different consumption needs. The problem is copy-paste implementation of that split, not the split itself.
